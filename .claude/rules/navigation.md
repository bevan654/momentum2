# Navigation
- **Start with the map.** Read `CODEBASE_MAP.md` first for where things live and how they connect. If it disagrees with the Project Structure tree in `CLAUDE.md`, the map is current: trust the map.
- **Scout before non-trivial changes.** Delegate to the `codebase-scout` subagent to find all affected code and what else must change, then make the edits in the main session. A change is non-trivial if it does any of these: touches more than one source file; renames, moves or deletes something; edits anything in the map's Load-bearing section; or touches data (Supabase tables, columns, RPCs), navigation (tabs, routes) or config (`app.config.ts`, env vars). Skip the scout for lookups that take a few tool calls.
- **Scout, not Explore.** For tracing impact, use `codebase-scout`, not the built-in `Explore` agent: the scout knows this map, the project rules and the connections LSP can't see.
- **LSP before grep.** For symbol lookups (definitions, references, callers), use the `LSP` tool first.
- **Remind people who haven't installed LSP.** The plugin is turned on for everyone in `.claude/settings.json`, but each person still has to install it once. At the start of a local session, if the `LSP` tool isn't available or reports `Executable not found`, tell the user once per session, before other work, in plain words:
  - **Why it helps:** without it, Claude finds connected code by text search. That's slower, uses more tokens, and can miss code or mix up different things with the same name, so a change is more likely to break something elsewhere. With it, Claude gets exact "where is this used" answers and sees type errors right after each edit.
  - **How to install** (once per computer): run `npm install -g typescript-language-server typescript` in a terminal, check it's found with `Get-Command typescript-language-server` (Windows) or `which typescript-language-server` (Mac), then install the plugin for yourself with `claude plugin install typescript-lsp@claude-plugins-official` (don't add `--scope project`: the shared settings file already turns it on) and start a new session from the repo root, so it reads `.claude/settings.json`.
  - Don't install it for them. Carry on with Grep/Glob in the meantime. Skip the reminder in web/cloud sessions, where LSP can't run.
- **Baseline errors aren't yours.** The repo has existing type errors before any change (see the map's Known baseline type errors section, and run `npx tsc --noEmit` for the current list). Don't fix them as part of other work: flag them and ask, like any existing bug, so the change keeps its scope.
- **No new unused code (Knip, every feature and fix).** Before handing work back, and again as part of the pre-PR review, run `npm run knip` (on Windows it needs the Microsoft Visual C++ runtime: `winget install Microsoft.VCRedist.2015+.x64`). A finding is the branch's own if the branch introduced it: the reported file, export, type or package was added by the branch, or the branch's diff (`git diff origin/main`) removed its last use. Those are the branch's to fix: remove it before opening the PR (an export nothing imports, a leftover file, a package that ended up unused), and tell the user what was removed. Everything else is pre-existing, even when it's in a file the branch edited: don't fix them as part of the change, just mention the count in the PR. The pre-PR reviewer gets the Knip output too and checks that nothing new slipped through. Mention the Knip result in the PR description.
- **Cleaning up unused code.** The main session runs `npm run knip` (the scout has no shell). Treat every result as a candidate, not proof: before deleting, have `codebase-scout` check each one for uses Knip can't see (route-name strings, `navigationBridge`, asset `require()`s, the dynamic `import()` in `FoodDetailModal`, config plugins in `app.config.ts`, native code in `modules/`/`targets/`, and scripts run by hand). Show the user the list and get a yes before deleting. Delete in small batches, one commit per batch, and run `npx tsc --noEmit` and the iOS bundle check after each one. If removing something makes a function parameter or prop pointless, remove it from the callers too. A prop a component ignores can be a lost feature, so flag it as a possible bug instead of deleting it silently.
- **Keep the map current.** When you add, move, rename or delete folders or modules, or change a tab or route, update `CODEBASE_MAP.md` in the same change. Every time the map changes, run `npm run check:map` and update its **Last verified** line (date + commit), as its Maintenance section says.
